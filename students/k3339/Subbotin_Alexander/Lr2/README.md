## Описание

Сравнение подходов `threading`, `multiprocessing` и `async` в Python на двух задачах:
CPU-bound вычисления и I/O-bound парсинг веб-страниц.

- uv

## Задача 1. Вычисление суммы чисел от 1 до 1 000 000 000

Каждая программа разбивает диапазон `[1, N]` на `cpu_count()` частей
и вычисляет частичные суммы параллельно.

### Описание подходов

| Подход | Модуль | Особенности |
|---|---|---|
| **Threading** | `threading` | Потоки разделяют память и GIL. Для CPU-bound задач GIL не даёт параллельного выполнения — потоки исполняются поочерёдно. |
| **Multiprocessing** | `multiprocessing` | Каждый процесс имеет свой GIL и адресное пространство. Истинный параллелизм для CPU-bound задач. Накладные расходы на создание процессов и IPC. |
| **Async** | `asyncio` | Однопоточная кооперативная многозадачность. Без `await`-точек задачи выполняются последовательно. Не подходит для CPU-bound задач. |

### Результаты (Apple M3 Pro, 10 ядер)

| Подход | Время (сек) |
|---|---|
| Threading | ~37 |
| Multiprocessing | ~6 |
| Async | ~33 |

### Выводы по задаче 1

- **Multiprocessing** показывает ускорение, пропорциональное числу ядер, т.к. обходит GIL.
- **Threading** не ускоряет CPU-bound задачи из-за GIL — потоки конкурируют за один lock, добавляя оверхед переключения.
- **Async** выполняется как последовательный код, т.к. в `calculate_sum` нет точек переключения (`await`).

## Задача 2. Параллельный парсинг веб-страниц

Парсинг 12 статей Wikipedia о финансовых категориях (Expense, Income, Budget, Saving и др.)
с сохранением заголовков и описаний в таблицу `categories` БД из Лабораторной работы 1.

### Описание подходов

| Подход | HTTP-клиент | БД-драйвер | Особенности |
|---|---|---|---|
| **Threading** | `requests` | `psycopg` (sync SQLAlchemy) | Потоки эффективны для I/O-bound задач: пока один поток ждёт ответа сети, другой работает. GIL отпускается на время I/O. |
| **Multiprocessing** | `requests` | `psycopg` (sync SQLAlchemy) | Каждый процесс создаёт своё соединение с БД. Высокий оверхед на создание процессов для лёгких I/O-задач. |
| **Async** | `aiohttp` | `asyncpg` (async SQLAlchemy) | Все запросы запускаются через `asyncio.gather` — истинная конкурентность на одном потоке без оверхеда переключения контекста ОС. |

### Результаты (Apple M3 Pro, 12 URL)

| Подход | Время (сек) |
|---|---|
| Threading | ~0.65 |
| Multiprocessing | ~1.70 |
| Async | ~0.77 |

### Выводы по задаче 2

- **Threading** и **Async** показывают сравнимую производительность для I/O-bound задач: GIL отпускается при ожидании I/O.
- **Multiprocessing** медленнее из-за накладных расходов на создание процессов, которые не окупаются при лёгких сетевых задачах.
- **Async** — предпочтительный подход для I/O-bound задач: минимальный расход памяти, отсутствие оверхеда потоков, масштабируется на тысячи одновременных соединений.

---

## Общий вывод

| Тип задачи | Лучший подход | Почему |
|---|---|---|
| CPU-bound | `multiprocessing` | Обходит GIL, истинный параллелизм на нескольких ядрах |
| I/O-bound | `asyncio` / `threading` | GIL отпускается при I/O; async эффективнее по памяти |
| Смешанный | `multiprocessing` + `asyncio` | Процессы для CPU, async для I/O внутри каждого процесса |
